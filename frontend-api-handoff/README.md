## Transport model

Frappe RPC over HTTP. Every endpoint is called as:

```
POST|GET  /api/method/<dotted.path.to.function>
```

GET endpoints take query parameters; POST endpoints take a JSON body.

### The envelope — two layers

Frappe wraps **every** whitelisted return value in an outer `message` object.
Inside it is the YOB envelope.

**Success:**

```json
{ "message": { "data": ..., "notice": "…", "meta": { "count": 3 } } }
```

- `data` is always present on success. It may be an object, an array, or `null`.
- `notice` is optional human-readable text. Do not branch on it.
- `meta` is optional (counts, pagination, warnings).

**Failure:**

```json
{ "message": { "errors": [ { "code": "cart_empty", "detail": "…", "field": "qty" } ] } }
```

- `errors` is always an array, even for one error.
- `code` is a stable lowercase `snake_case` machine value — **branch on this**.
- `detail` is human-readable and may change. Never parse it.
- `field` is present when the error belongs to a specific input.
- `details` is an optional object carrying structured extras (payment errors use
  it for `retryable` and `sales_order`).

**There is no `success` boolean.** Branch on HTTP status first, then on
`errors[0].code`.

### Raw Frappe failures

Some failures never reach the YOB envelope and arrive in Frappe's own shape —
notably an unauthenticated call to an authenticated endpoint, which returns
**403 with a raw traceback in `exc`**, because `@frappe.whitelist()` rejects
Guest before YOB code runs. Your network layer must tolerate a response with no
`message.errors` array and normalise it. Never display `exc` or
`_server_messages` to a user.

### CSRF

Frappe's own CSRF applies to **non-GET authenticated** calls. Send the token
from login or `get_session_context` as:

```
X-Frappe-CSRF-Token: <token>
```

Public payment endpoints are `allow_guest` and do not require it.

## The one distinction that matters most

```
AUTHENTICATED STOREFRONT              PUBLIC PAYMENT
catalog, cart, addresses,             /payment/<token>
checkout, proceed_to_payment          get_checkout_data, process_payment,
                                      verify_payment
requires sid cookie + CSRF            requires NO session at all
```

`/payment/<token>` is **intentionally public**. A payer may open it from a
shared link, an email, or an incognito window with no storefront login. The
token is the credential for one exact Payment Request.

**Do not place the payment route behind a session guard.** See
`AUTHORIZATION-MATRIX.md`.

## OpenAPI limitations

Frappe's RPC style does not map perfectly onto OpenAPI:

- every path is `/api/method/<dotted.path>` rather than a REST resource;
- the outer `message` wrapper is modelled, but `data` is often loosely typed
  because several endpoints return whole documents;
- one endpoint can answer several statuses (`proceed_to_payment` returns 200 or
  201) — both are documented;
- Frappe accepts GET query params for some POST-declared methods at the
  framework level; the **declared** method in this package is the one enforced
  by `methods=[…]` and is what you should use.

Where precision was not achievable, the prose contract is authoritative.

deleting them is a repository decision rather than a documentation one. If you
find a disagreement, **this package wins** — it was generated by executing the
current code.

## Frontend synchronization checklist

Run through this after importing the package:

- [ ] Compare DTO interfaces against `openapi.json` schemas and `examples/`
- [ ] Compare endpoint dotted paths against `AUTHORIZATION-MATRIX.md`
- [ ] **Cart setters** return an acknowledgement, not a Cart — confirm a
      follow-up `get_cart` exists after each setter
- [ ] Confirm `add_to_cart` / `remove_from_cart` responses are parsed as a
      **flat Cart document**, not as the `get_cart` envelope
- [ ] **`add_to_cart` `qty` is a DELTA** — confirm the quantity stepper sends the
      difference, not the new total, and that the call is not auto-retried
- [ ] Confirm `is_shippable` is re-read from every Cart response
- [ ] Confirm route guards: payment route **outside** the session guard
- [ ] Confirm `process_payment` sends only `token` and `payment_method`
- [ ] Confirm `payment_method` is the Payment Method **`name`**, not `method_code`
- [ ] Confirm `proceed_to_payment` handles **both** 200 and 201 as success
- [ ] Confirm paid / revoked-token handling
- [ ] Confirm Razorpay loader URL, options, and that `amount` is passed
      unchanged (it is already in paise)
- [ ] Confirm the token is never written to `localStorage` / `sessionStorage`
- [ ] **Orders:** remove any `billing_address.*` / `shipping_address.*` object
      binding — those objects no longer exist. Bind `*_address_display` and
      render as **plain text** (`white-space: pre-line`), never `[innerHTML]`
- [ ] **Orders:** format each list row with `row.currency`; delete any
      environment/default-currency fallback
- [ ] **Orders:** remove any client-side sort of the order list — the server
      returns `creation` desc, and `creation` is not in the response
- [ ] **Account:** `update_address` sends only the edited fields. Remove any
      "resend the whole object so nothing is lost" workaround, and make sure the
      payload is **not** padded with `""` — that now *clears* those fields
- [ ] **Account:** handle **409** `address_in_use` / `contact_in_use` as its own
      outcome — the record still exists, stays in the list, and is not retryable
- [ ] **Account:** no automatic retry on `delete_address` / `delete_contact`;
      on an uncertain delete, re-read the list instead
- [ ] **Account:** re-read the list after a successful mutation, and drop any
      cache-busting/delay workaround — the server invalidates its own cache
- [ ] Compare error mappings against `ERROR-CODES.md`
- [ ] Update mock/fixture data to match `examples/`
- [ ] Run unit + E2E + build

This is a checklist for the frontend repository. Nothing in this package
modifies Angular.
